How Proof Key of Code Exchange works: PKCE


When the client sends the user to the authorization server i.e. Facebook, Google, etc, to approve the client being able to use the user’s data, it creates a random string, which the documentation calls the code verifier, and a hash of that string, which it calls the code challenge. The client sends along the code challenge as a query param when it sends the user to the authorization server, so that the authorization server has it on hand.  The client holds on to the code verifier. If the user allows the client access to their data, the authorization server will send the user back to the redirect URL with the authorization code. At this point, the authorization server is just praying that the code ends up in the right hands, but can never be sure.  When the client redeems that authorization code for the access token it sends the code verifier (the original string) along with the request. The authorization server hashes the string, compares it to the hash it has i.e. the code challenge, and if it matches, it knows that the entity redeeming the code for the token is the same that requested the token because it has both sides of the broken heart.


Why doesn’t the authorization server just give the client the access token to begin with ?  Because it’s not safe for the access token to go over the front channel where it can be intercepted and may or may not land where it is supposed to land.  Instead it gives the client a code which it can redeem for the actual token, as long as the client can prove it is the entity that requested the code using something like PKSE.
